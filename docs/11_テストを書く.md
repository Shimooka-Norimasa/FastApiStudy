## 11-1. なぜテストを書くのか

ここまで、コードを変えるたびにブラウザで「追加できるか」「削除できるか」「エラーが出るか」を手で確かめてきました。
機能が増えるほど、この確認は大変になり、見落としも出てきます。

**自動テスト** は、この確認作業をプログラムにしたものです。

```
手で確認:   ブラウザを開く → 入力する → ボタンを押す → 目で見る …… を毎回くり返す
自動テスト: pytest と打つ → 数秒で全部の確認が終わる → 結果が passed / failed で出る
```

特に、**動きを変えずにコードを書き換える（リファクタリング）** ときに威力を発揮します。
次の第12章では、データベースの操作を丸ごと書き換えます。その前にテストを用意しておけば、「書き換えても前と同じように動く」ことをすぐに確かめられます。

## 11-4. pytest の基本

pytest は、**`test_` で始まるファイル** の中の **`test_` で始まる関数** を自動で探して実行します。

```python
def test_足し算():
    assert 1 + 1 == 2
```

- `assert 条件` … 条件が正しければ何も起きず、間違っていればテスト失敗になる
- 関数名には日本語も使えます。**何を確かめるテストなのか** がわかる名前を付けると、失敗したときに原因がすぐわかります

## 11-5. TestClient

`TestClient` を使うと、**サーバーを起動せずに** アプリへリクエストを送れます。

```python
from fastapi.testclient import TestClient
from main import app

client = TestClient(app)
response = client.get("/api/todos")       # GET を送る
response = client.post("/api/todos", json={"title": "牛乳"})   # JSON を付けて POST

response.status_code    # ステータスコード（200 など）
response.json()         # 返ってきた JSON（Python の辞書やリストになる）
response.text           # 返ってきた本文（HTML など）
```

## 11-6. テスト用のデータベースを使う（`conftest.py`）

テストのたびに本物の `todo.db` にデータを追加・削除されては困ります。
また、前のテストで追加したデータが残っていると、結果が変わってしまいます。
そこで **テストごとに空のデータベースを用意** します。

```python
import pytest
from fastapi.testclient import TestClient

import database
from main import app


@pytest.fixture
def client(tmp_path, monkeypatch):
    """テスト専用の空のデータベースを使う TestClient を用意する"""
    monkeypatch.setattr(database, "DB_NAME", str(tmp_path / "test.db"))

    with TestClient(app) as test_client:
        yield test_client
```

### fixture（フィクスチャ）とは

`@pytest.fixture` を付けた関数は **テストの準備をする関数** です。
テスト関数の引数に **同じ名前** を書くと、pytest が準備した値を渡してくれます。

```python
def test_追加できる(client):   # ← conftest.py の client() の結果が渡される
    ...
```

第8章の Depends とよく似た仕組みです（引数に書くだけで用意してもらえる、`yield` の後で後片付けできる）。
`conftest.py` に書いた fixture は、同じフォルダのすべてのテストファイルから使えます。

### pytest が用意してくれる fixture

`client` 自体も、pytest が最初から用意している fixture を引数で受け取っています。

| fixture | 役割 |
|---|---|
| `tmp_path` | テストごとに新しい一時フォルダを用意してくれる（テストが終わると不要になる） |
| `monkeypatch` | テスト中だけ値を差し替え、テストが終わったら元に戻してくれる |

`monkeypatch.setattr(database, "DB_NAME", ...)` で、`database.py` の `DB_NAME` を
一時フォルダの `test.db` に差し替えています。`get_connection()` は呼ばれるたびに `DB_NAME` を見るので、
テスト中のアクセスはすべて `test.db` に向かいます。

`with TestClient(app) as test_client:` と `with` で使うと、起動時の処理（`lifespan` の `init_db()`）も実行され、
テーブルが作られます。

> **別の方法: `dependency_overrides`**
> FastAPI には、Depends の関数を差し替える `app.dependency_overrides` という仕組みもあります。
> ```python
> app.dependency_overrides[database.get_db] = テスト用の関数
> ```
> 第8章で「Depends は差し替えができる」と書いたのはこのことです。
> この教材では、より簡単な `monkeypatch` を使っています。

## 11-7. テストを書く（`test_main.py`）

### 基本形: 送る → 確かめる

```python
def test_追加できる(client):
    response = client.post("/api/todos", json={"title": "牛乳を買う"})
    assert response.status_code == 201
    assert response.json() == {"id": 1, "title": "牛乳を買う", "done": False}
```

毎回空のデータベースから始まるので、最初に追加した ToDo の id は必ず 1 になります。

### 準備 → 操作 → 確認

```python
def test_完了にできる(client):
    client.post("/api/todos", json={"title": "牛乳を買う"})            # 準備

    response = client.patch("/api/todos/1", json={"done": True})    # 操作
    assert response.status_code == 200                               # 確認
    assert response.json() == {"id": 1, "title": "牛乳を買う", "done": True}
```

テストは「準備 → 操作 → 確認」の3段で書くと読みやすくなります（空行で区切ると見やすい）。

### エラーのテスト

```python
def test_存在しないToDoは404(client):
    response = client.get("/api/todos/999")
    assert response.status_code == 404
    assert response.json() == {"detail": "指定された ToDo が見つかりません"}
```

**うまくいかない場合が正しくエラーになるか** も大切なテストです。

### parametrize: 値を変えて何度もテストする

```python
@pytest.mark.parametrize("title", ["", "   ", "あ" * 101])
def test_不正なタイトルは追加できない(client, title):
    response = client.post("/api/todos", json={"title": title})
    assert response.status_code == 422
    assert client.get("/api/todos").json() == []
```

`@pytest.mark.parametrize("引数名", [値1, 値2, ...])` を付けると、値ごとにテストが実行されます。
この例では「空文字」「空白だけ」「101文字」の3回です。`"あ" * 101` は「あ」を101個つなげた文字列です。

### 境界値

```python
def test_100文字ちょうどは追加できる(client):
    response = client.post("/api/todos", json={"title": "あ" * 100})
    assert response.status_code == 201
```

「101文字はダメ」と「100文字はOK」の両方を確かめておくと、`max_length=100` を `max_length=99` と書き間違えたときに気づけます。
このように、**ルールの境目の値（境界値）** はバグが起きやすいので、テストしておくのがおすすめです。

### 画面のテスト

```python
def test_存在しないページはHTMLのエラー画面になる(client):
    response = client.get("/no-such-page")
    assert response.status_code == 404
    assert "エラー 404" in response.text
```

`in` は「文字列の中に含まれているか」を調べます。HTML 画面も、このように確かめられます。

## まとめ

- テスト = 確認作業をプログラムにしたもの。`pytest` で一度に実行できる
- `test_` で始まる関数に `assert` で「こうなるはず」を書く
- `TestClient` でサーバーを起動せずにリクエストを送れる
- fixture でテストの準備を共通化し、`tmp_path` と `monkeypatch` で毎回まっさらなデータベースを使う
- エラーになるべき場合や、境界値もテストする
