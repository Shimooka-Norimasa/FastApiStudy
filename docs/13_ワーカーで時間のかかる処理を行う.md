# 第13章 ワーカーで時間のかかる処理を行う

## この章のねらい

- 時間のかかる処理を、Web アプリとは **別のプログラム（ワーカー）** に任せる仕組みを理解する
- キュー（仕事の待ち行列）とワーカーを **自分で作って**、中で何が起きているのかを知る

## この章が終わるとできること

- 「受け付けたらすぐ返事をして、処理は裏でワーカーが行う」アプリが作れる
- データベースのテーブルをキューとして使い、仕事の状態（待ち・実行中・完了・失敗）を管理できる
- ブラウザから仕事の状態を定期的に確認し（ポーリング）、終わったら結果をダウンロードできる
- ワーカーのフレームワーク（Celery など）が何をしてくれるものなのか説明できる

## 13-2. なぜワーカーが必要なのか

### 時間のかかる処理をそのまま書くと

```python
@app.post("/api/exports")
def create_export():
    time.sleep(5)          # 5秒かかる処理
    return {"message": "できました"}
```

こう書くと、ボタンを押してから **5秒間、何の反応もありません**。
実際のアプリでは、大量データの集計、メールの一斉送信、画像や動画の変換など、数十秒〜数分かかる処理もあります。

- 利用者は「固まった？」と思って何度もボタンを押してしまう
- ブラウザやサーバーの制限時間を超えると、途中で切られてしまう
- 処理中に Web サーバーを再起動すると、処理も一緒に止まってしまう

### ワーカーの考え方

そこで、役割を分けます。

```
   ブラウザ                Web アプリ（uvicorn）           キュー（jobs テーブル）         ワーカー（worker.py）
      │  ① 書き出して！            │                               │                              │
      │ ─────────────────────────▶ │  ② 仕事を登録（待ち）          │                              │
      │                            │ ─────────────────────────────▶ │                              │
      │  ③ 受け付けました（仕事1）  │                               │  ④ 待ちの仕事を取り出す       │
      │ ◀───────────────────────── │                               │ ◀─────────────────────────── │
      │                            │                               │                              │ ⑤ 実行（5秒）
      │  ⑥ 仕事1はどう？            │                               │  ⑦ 完了と書き込む             │
      │ ─────────────────────────▶ │ ── 状態を読む ──────────────▶  │ ◀─────────────────────────── │
      │  ⑧ 完了！                  │                               │                              │
      │ ◀───────────────────────── │                               │                              │
```

| 登場人物 | 役割 | たとえ（クリーニング店） |
|---|---|---|
| Web アプリ | 注文を受け付けて、すぐに受付番号を返す。状態を聞かれたら答える | 受付カウンター |
| キュー | まだ処理していない仕事の一覧 | 預かり伝票の束 |
| ワーカー | キューから仕事を1つずつ取り出して実行する | 奥の作業場の職人 |

受付カウンターは注文を受けたら引換券を渡すだけなので、お客さんを待たせません。
作業場が忙しくても、受付は止まりません。

## 13-3. まずは FastAPI の BackgroundTasks

実は FastAPI には、**レスポンスを返した後に処理を実行する** `BackgroundTasks` という機能が最初から入っています。

```python
from fastapi import BackgroundTasks


def send_email(address: str):
    time.sleep(5)   # メール送信など、時間のかかる処理
    print(f"{address} に送信しました")


@app.post("/send")
def send(background_tasks: BackgroundTasks):
    background_tasks.add_task(send_email, "taro@example.com")   # 「後でこれを実行して」と予約
    return {"message": "受け付けました"}   # すぐに返事が返る
```

引数に `BackgroundTasks` と書くと FastAPI が用意してくれて（第8章の Depends と同じような仕組み）、
`add_task(関数, 引数...)` で予約した関数は、レスポンスを返した後に実行されます。

数行で書けてとても便利ですが、次のような **限界** があります。

| 限界 | 理由 |
|---|---|
| Web サーバーを止めると、実行中・予約中の処理が消える | 処理が Web アプリと同じプログラムの中で動いているため。予約はメモリにしか無い |
| 失敗したときにやり直す仕組みが無い | 予約した関数を実行するだけなので |
| 処理の状態（終わったかどうか）を知る方法が無い | 結果をどこにも記録しないので |
| 重い処理が増えると、Web アプリ自体が遅くなる | 同じプログラムの中で、CPU やメモリを取り合うため |

「ログを書く」「確認メールを1通送る」など、**短くて、消えても困らない処理** には BackgroundTasks で十分です。
そうでない処理には、この章で作るワーカーを使います。

## 13-5. キューを作る（`database.py`）

キュー専用のソフトを使わなくても、**データベースのテーブル** をキューとして使えます。

```python
PENDING = "pending"   # 待ち（ワーカーに取り出されるのを待っている）
RUNNING = "running"   # 実行中
DONE = "done"         # 完了
FAILED = "failed"     # 失敗


class JobRow(SQLModel, table=True):
    __tablename__ = "jobs"

    id: int | None = Field(default=None, primary_key=True)
    status: str = PENDING
    result_file: str | None = None   # 完了したときに作られたファイルの名前
    error: str | None = None         # 失敗したときのエラーメッセージ
```

状態は次のように移り変わります。

```
             ワーカーが取り出す           処理が成功
  待ち ──────────────────────▶ 実行中 ────────────────▶ 完了
 pending                       running        │          done
    ▲                                         │ 処理中にエラー
    │  ワーカーが途中で止まった                  └──────────────▶ 失敗
    └───── （起動時に戻す） ───────────                          failed
```

状態の文字列を `PENDING` などの定数にしているのは、`"pending"` を `"pendng"` と書き間違えても Python はエラーにしてくれませんが、
`database.PENDNG` と書き間違えればエラーになって気づけるからです。

### 仕事の登録（Web アプリ側）

```python
def add_job(session: Session) -> JobRow:
    job = JobRow()           # status は自動で "pending" になる
    session.add(job)
    session.commit()
    session.refresh(job)
    return job
```

### 仕事の取り出し（ワーカー側）

ここがキューでいちばん大事なところです。

```python
def claim_next_job(session: Session) -> JobRow | None:
    while True:
        statement = (
            select(JobRow)
            .where(JobRow.status == PENDING)
            .order_by(col(JobRow.id))
            .limit(1)
        )
        job = session.exec(statement).first()
        if job is None:
            return None   # 待ちの仕事が無い

        result = session.exec(
            update(JobRow)
            .where(col(JobRow.id) == job.id, col(JobRow.status) == PENDING)
            .values(status=RUNNING)
        )
        session.commit()
        if result.rowcount == 1:
            session.refresh(job)
            return job
```

1. 「待ち」の仕事を、id の小さい順（＝登録が古い順）に1件だけ探す（`.limit(1)` は1件だけ、`.first()` は最初の1件を取り出す）
2. 見つかったら、`UPDATE jobs SET status = 'running' WHERE id = ? AND status = 'pending'` を実行する
3. 書き換えられた行数（`rowcount`）が 1 なら、自分がその仕事を取れた

**なぜ2の条件に `status = 'pending'` も付けるの？**
ワーカーを2つ動かしていると、2つが同時に同じ仕事を見つけることがあります。

```
ワーカーA: 仕事1を見つけた ─┐
ワーカーB: 仕事1を見つけた ─┤
ワーカーA: 「仕事1がまだ待ちなら実行中にする」→ 1行書き換えた → 取れた！
ワーカーB: 「仕事1がまだ待ちなら実行中にする」→ もう待ちではないので 0行 → 取れなかった。次を探す
```

条件付きの UPDATE は1つずつ順番に実行されるので、**同じ仕事を2回実行することがなくなります**。
これはキューを作るときの定番のテクニックです。

`update(...)` は `UPDATE` 文を作る SQLModel の関数です。第12章の「属性を書き換えて commit」と違い、条件に合う行をまとめて書き換えられ、書き換えた行数もわかります。

### 完了・失敗・やり直し

```python
def finish_job(session: Session, job: JobRow, result_file: str):
    job.status = DONE
    job.result_file = result_file
    session.add(job)
    session.commit()


def requeue_running_jobs(session: Session) -> int:
    result = session.exec(
        update(JobRow).where(col(JobRow.status) == RUNNING).values(status=PENDING)
    )
    session.commit()
    return result.rowcount
```

ワーカーが処理の途中で止まる（Ctrl + C、PC の電源が落ちる など）と、その仕事は「実行中」のまま残ってしまいます。
`requeue_running_jobs` は、そういう仕事を「待ち」に戻す関数で、ワーカーの起動時に呼びます。

> この方法は **ワーカーを1つだけ動かす** 前提です。ワーカーが2つあると、もう1つのワーカーが本当に実行中の仕事まで待ちに戻してしまいます。
> 複数のワーカーで正しく扱うには「最後に生きている合図を送った時刻」を記録するなどの工夫が必要になります。こうした面倒な部分を引き受けてくれるのが、後のコラムで紹介するフレームワークです。

## 13-6. 時間のかかる処理（`tasks.py`）

```python
import csv
import time
from pathlib import Path

EXPORT_DIR = "exports"
WAIT_SECONDS = 5


def export_todos_csv(session: Session, job_id: int) -> str:
    time.sleep(WAIT_SECONDS)

    folder = Path(EXPORT_DIR)
    folder.mkdir(exist_ok=True)
    file_name = f"todos_{job_id}.csv"

    with open(folder / file_name, "w", encoding="utf-8-sig", newline="") as f:
        writer = csv.writer(f)
        writer.writerow(["id", "タイトル", "状態"])
        for todo in reversed(database.get_all_todos(session)):
            writer.writerow([todo.id, todo.title, "完了" if todo.done else "未完了"])

    return file_name
```

| 部分 | 説明 |
|---|---|
| `time.sleep(5)` | 5秒待つ。重い処理のふり |
| `Path(EXPORT_DIR)` | ファイルやフォルダの場所を表すオブジェクト。`/` でつなげられる（`folder / file_name`） |
| `folder.mkdir(exist_ok=True)` | フォルダを作る。すでにあってもエラーにしない |
| `csv.writer(f)` | Python 標準の csv モジュール。`writerow([...])` で1行書き出す |
| `encoding="utf-8-sig"` | Excel で開いても日本語が文字化けしない形式 |
| `reversed(...)` | 並びを逆にする（一覧は新しい順なので、古い順に直している） |

このファイルには「ワーカーの仕組み」は何も書いていません。**ただの関数** です。
処理の中身（`tasks.py`）と、仕事を取り出して実行する仕組み（`worker.py`）を分けておくと、処理を増やすのも、テストするのも簡単になります。

## 13-7. ワーカー（`worker.py`）

```python
def process_one_job() -> bool:
    """仕事を1件処理する。処理した仕事があれば True、無ければ False を返す"""
    with Session(database.engine) as session:
        job = database.claim_next_job(session)
        if job is None:
            return False

        print(f"仕事 {job.id} を開始します")
        try:
            result_file = tasks.export_todos_csv(session, job.id)
        except Exception as error:
            database.fail_job(session, job, str(error))
            print(f"仕事 {job.id} は失敗しました: {error}")
        else:
            database.finish_job(session, job, result_file)
            print(f"仕事 {job.id} が完了しました: {result_file}")
        return True
```

- ワーカーは Web アプリではないので Depends は使えません。`with Session(database.engine) as session:` で自分でセッションを作ります。
- `try` / `except Exception as error:` … `try` の中で **どんな種類のエラー** が起きても `except` の中が実行され、`error` にそのエラーが入ります。
  エラーが起きても **ワーカー自体は止まらず**、その仕事を「失敗」として記録して次の仕事に進めます。
- `else:` … `try` の中でエラーが **起きなかったときだけ** 実行されます。

```python
def main():
    database.init_db()

    with Session(database.engine) as session:
        count = database.requeue_running_jobs(session)
        if count:
            print(f"途中で止まっていた仕事 {count} 件を、待ちに戻しました")

    print("ワーカーを起動しました（止めるときは Ctrl + C）")
    try:
        while True:
            if not process_one_job():
                time.sleep(POLL_SECONDS)
    except KeyboardInterrupt:
        print("ワーカーを止めました")


if __name__ == "__main__":
    main()
```

- `while True:` … **ずっとくり返す** ループ。ワーカーは基本的に止めるまで動き続けます。
- 仕事が無いときは1秒待ってから、もう一度キューを確認します。待たないと、空のキューを1秒に何千回も確認して PC に無駄な負担をかけてしまいます。
- `KeyboardInterrupt` … Ctrl + C を押したときに起きる例外です。これを受け取って、メッセージを出してきれいに終わります。
- `if __name__ == "__main__":` … 「このファイルが `python worker.py` で **直接実行されたときだけ**」という意味の決まり文句です。テストから `import worker` したときに、ループが始まってしまうのを防ぎます。

## 13-8. Web アプリ側の API（`exports_api.py`）

| メソッド | URL | 処理 | 成功時のコード |
|---|---|---|---|
| POST | `/api/exports` | 仕事を登録する | 202 |
| GET | `/api/exports/{job_id}` | 仕事の状態を返す | 200 |
| GET | `/api/exports/{job_id}/download` | できたファイルを返す | 200 |

```python
@router.post("", response_model=Job, status_code=202)
def create_export(session: SessionDep):
    return database.add_job(session)
```

Web アプリは仕事を **登録するだけ** で、CSV を作る処理は呼びません。だからすぐに返事が返ります。
**202 Accepted** は「受け付けた。でも処理はまだ終わっていない」という意味のステータスコードです。

```python
@router.get("/{job_id}/download")
def download_export(job_id: int, session: SessionDep):
    job = get_job_or_404(session, job_id)
    if job.status != database.DONE or job.result_file is None:
        raise HTTPException(status_code=409, detail="まだファイルができていません")

    path = Path(tasks.EXPORT_DIR) / job.result_file
    return FileResponse(path, filename=job.result_file, media_type="text/csv")
```

- `FileResponse` … ファイルをそのまま返すレスポンス。`filename` を付けると、ブラウザはダウンロードとして扱います。
- **409 Conflict** … 「今の状態ではその操作はできない」という意味。完了前にダウンロードしようとしたときに返します。

`schemas.py` には、返す JSON の形を追加しました。


## 13-9. 画面側: ポーリング（`static/app.js`）

ブラウザは、仕事が終わったかどうかを **一定時間ごとに聞きに行きます**。これを **ポーリング** といいます。

```javascript
async function startExport() {
  const job = await callApi("POST", "/api/exports");
  exportButton.disabled = true;
  showExportStatus(job);
  setTimeout(() => checkExport(job.id), 1000);
}

async function checkExport(jobId) {
  const job = await callApi("GET", `/api/exports/${jobId}`);
  showExportStatus(job);
  if (job.status === "pending" || job.status === "running") {
    setTimeout(() => checkExport(jobId), 1000);   // まだなら1秒後にもう一度
  } else {
    exportButton.disabled = false;
  }
}
```

（実際のコードには、エラー時の処理も入っています）

- `setTimeout(関数, 1000)` … 1000ミリ秒（1秒）後に関数を1回実行する
- `exportButton.disabled = true` … ボタンを押せなくする（仕事を何個も登録しないように）
- 終わったら `showExportStatus` がダウンロードのリンクを表示します

ワーカーも「キューに仕事が来たか」を1秒ごとに確認していました。**ブラウザもワーカーも、ポーリングで状態の変化を知っている** わけです。

## 13-11. テスト（`test_worker.py`）

ワーカーはずっと動き続けるプログラムですが、テストでは `process_one_job()` を呼んで **1件だけ処理させる** ことで確かめます。
`main()` のループと `process_one_job()` を分けておいたのは、このためでもあります。

```python
def test_ワーカーが処理すると完了になる(client):
    client.post("/api/exports")

    assert worker.process_one_job() is True
    assert client.get("/api/exports/1").json()["status"] == "done"
```

失敗した場合のテストでは、`monkeypatch` で処理の関数を「必ずエラーになる関数」に差し替えています。

```python
def test_処理中にエラーが起きると失敗になる(client, monkeypatch):
    def broken_export(session, job_id):
        raise RuntimeError("ディスクがいっぱいです")

    monkeypatch.setattr(tasks, "export_todos_csv", broken_export)
    client.post("/api/exports")

    assert worker.process_one_job() is True   # ワーカー自体は止まらない
    assert client.get("/api/exports/1").json() == {
        "id": 1,
        "status": "failed",
        "error": "ディスクがいっぱいです",
    }
```

本物のディスクをいっぱいにしなくても、エラーが起きたときの動きを確かめられます。

## コラム: ワーカーのフレームワーク

この章ではワーカーを自作しましたが、実際の開発では **ワーカーのフレームワーク（タスクキュー）** を使うのが一般的です。
自作してみたことで、フレームワークが何をしてくれるのかがわかるはずです。

### フレームワークが肩代わりしてくれること

| 自作版でやったこと／できなかったこと | フレームワークでは |
|---|---|
| jobs テーブルを作り、登録・取り出し・状態の更新を書いた | 関数に印（デコレーター）を付けて呼ぶだけで、キューへの登録と実行をしてくれる |
| 同じ仕事を2回取らない工夫を自分で書いた | 最初から考慮されている |
| ワーカーは1つ前提（やり直しの仕組みのため） | たくさんのワーカーを、複数の PC で動かせる |
| やり直しは練習問題（自分で書く） | 回数や間隔を指定するだけで自動でやり直す |
| 定期実行はできない | 「毎朝9時に実行」などの定期実行ができるものが多い |
| 様子はターミナルの表示だけ | 状態を見るための管理画面が用意されているものもある |

### 代表的なフレームワーク

| 名前 | 特徴 | 必要なもの | Windows |
|---|---|---|---|
| **Celery** | Python で最も有名で、実務での利用例・情報が多い | RabbitMQ や Redis などの **メッセージブローカー**（仕事を中継する専用サーバー） | Celery 4 以降は公式には非対応 |
| **RQ**（Redis Queue） | シンプルで覚えることが少ない | Redis | ワーカーは直接は動かない（WSL を使う） |
| **Huey** | 軽量。Redis のほか、SQLite でも動かせる | Redis または SQLite など | — |
| **Taskiq** | `async` / `await`（非同期）に対応した新しめのフレームワーク。FastAPI と組み合わせやすい | Redis や RabbitMQ など。ZeroMQ を使えば専用サーバーなしでも動く | ZeroMQ を使う場合は追加のライブラリ（tornado）が必要 |

（2026年10月時点の各公式ドキュメントの情報です。Huey の Windows での動作は確認していません。Taskiq は ZeroMQ を使う構成で、この PC で動作を確認しました）

使い方のイメージ（Celery の例）:

```python
from celery import Celery

app = Celery("tasks", broker="redis://localhost:6379/0")


@app.task          # この印を付けるだけで「ワーカーで実行できる関数」になる
def export_todos_csv(job_id):
    ...


export_todos_csv.delay(1)   # キューに登録（ワーカーが実行してくれる）
```

```powershell
celery -A tasks worker      # ワーカーの起動
```

`@app.task` が自作版の jobs テーブルと `claim_next_job`、`celery ... worker` が `worker.py` にあたります。

> **Redis と Windows**
> 多くのフレームワークは **Redis**（データをメモリに置く、高速なデータベース）を必要とします。
> Redis は Windows 版が公式には提供されていないため、Windows では WSL（Windows の中で Linux を動かす仕組み）や Docker を使うのが一般的です。
> この教材で自作ワーカーを選んだのは、追加のソフトを入れずに PC 1台で動かせるようにするためでもあります。

> **Taskiq を専用サーバーなしで使うときの注意**
> ZeroMQ を使う構成では、仕事はどこにも保存されません。ワーカーが止まっている間に登録した仕事は **消えてしまいます**。
> また、ワーカーは1つしか動かせません（複数動かすと、同じ仕事がワーカーの数だけ実行されます）。
> 学習用やちょっとした用途向けで、仕事を確実に処理したい場合は Redis などと組み合わせて使います。

### どれを選べばいい？

- **学習用・PC 1台で動かす** → この章の自作版、または FastAPI の BackgroundTasks
- **解説記事などの情報が多いものを使いたい** → Celery
- **シンプルに始めたい** → RQ や Huey
- **FastAPI の async に合わせたい** → Taskiq

どれを使う場合でも、この章で学んだ「キュー」「ワーカー」「状態」「失敗したときの扱い」という考え方はそのまま役に立ちます。

## コラム: もう1つの「ワーカー」― uvicorn の `--workers`

「ワーカー」という言葉は、別の意味でも使われます。

```powershell
uvicorn main:app --workers 4
```

これは **同じ Web アプリを4つのプロセス（プログラム）で同時に動かす** という意味です。
1つのプロセスでは手が回らないほどアクセスが多いときに、手分けして受け付けます。

| | この章のワーカー | uvicorn の `--workers` |
|---|---|---|
| 何をするか | 時間のかかる **処理** を、Web アプリとは別に実行する | **リクエストの受け付け** を、複数のプロセスで手分けする |
| 動くプログラム | `worker.py`（Web アプリとは別物） | 同じ Web アプリ（`main.py`）が複数 |
| 目的 | 利用者を待たせない、処理を確実に行う | たくさんのアクセスをさばく |

> `--workers` は `--reload` と一緒には使えません。開発中は `--reload`、本番では `--workers` と使い分けます。
> また、複数のプロセスはメモリを共有しないので、第4章のように Python のリストにデータを入れておく方法は使えません（プロセスごとに別々のリストになってしまう）。
> データベースに保存しておくのは、この点でも大切です。

## まとめ

- 時間のかかる処理は、Web アプリとは別のプログラム（ワーカー）に任せる
- Web アプリは仕事を **キュー** に登録してすぐに返事（202）をし、ワーカーがキューから取り出して実行する
- データベースのテーブルをキューにすれば、ワーカーが止まっていても仕事は消えない
- 「まだ待ちなら実行中にする」という条件付きの UPDATE で、同じ仕事の二重実行を防ぐ
- エラーが起きてもワーカーは止めず、「失敗」として記録する
- ブラウザはポーリングで仕事の状態を確認する
- 実際の開発では Celery などのフレームワークを使うことが多い。中でやっていることは自作版と同じ
